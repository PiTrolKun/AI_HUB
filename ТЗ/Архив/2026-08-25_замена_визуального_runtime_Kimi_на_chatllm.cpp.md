# ТЗ: замена визуального runtime Kimi на chatllm.cpp

Дата: 2026-08-25
Статус: выполнено и принято пользователем
Версия разработки: `0.1.4-dev`

## 1. Причина и цель

Текущий тракт `Kimi-VL GGUF + mmproj + llama.cpp b9442` запускается технически,
но на двух контрольных изображениях дал грубую смысловую подмену сцены. Простая
формулировка prompt, снятие ограничения ответа и увеличение визуального бюджета
это не исправили.

Изолированный контроль той же модели через `chatllm.cpp v24` и отдельную
конвертацию GGMM Q4_1 правильно распознал оба изображения. Цель задачи — сделать
этот подтверждённый тракт штатным визуальным runtime Среднего комплекта, не
удаляя прежние файлы и сохраняя понятный путь отката.

## 2. Подтверждённая основа решения

- runtime: `chatllm.cpp v24`, commit
  `f5f1d25365fb59447eb58994030c5acd492fcd53`;
- API: собственный loopback-сервер `server.exe`, маршрут
  `/v1/chat/completions`;
- модель: `kimi-vl-thinking-2506-q4_1.bin`;
- размер: `10447149104` байт;
- SHA-256:
  `33700EA2F4C8467FBCC4EFA060C763E035A8E73003424634125B5A3C64CE02C9`;
- источник: ModelScope `judd2024/chatllm_quantized_kimi-vl`;
- обработка изображений: portable ImageMagick `7.1.2-30 Q16-HDRI x64`;
- проверенный CPU-профиль: до 24 потоков, `batch_size=512`, контекст `4096`,
  `max_proj_length=1024`, без искусственного лимита новых токенов;
- GPU-offload в эту задачу не входит: на RTX 4090 проверенные варианты были
  медленнее CPU либо не помещались в VRAM.

## 3. Границы задачи

Входит:

- отдельный путь и паспорт backend-а `chatllm.cpp`;
- поставка backend-а и его ImageMagick-зависимости вместе с будущим
  установщиком;
- новая управляемая карточка Kimi в совместимом формате GGMM Q4_1;
- многопоточная возобновляемая загрузка точного файла по закреплённым размеру и
  SHA-256;
- перевод Среднего комплекта и runtime-проверки Kimi на новый backend;
- использование собственного OpenAI-совместимого server API `chatllm.cpp`;
- очистка служебного блока размышлений до передачи отчёта ядру;
- отмена, таймаут, завершение дочернего процесса и безопасный loopback;
- автоматические тесты аргументов, запроса и разбора ответа;
- локальный живой smoke-test на уже проверенном файле;
- обновление версии, реестра зависимостей и истории проекта.
- замена служебной роли ядра на реальную издательскую роль с ясной целью
  описания изображения и отдельным параметром языка результата.

Не входит:

- удаление прежних GGUF/mmproj-файлов Kimi;
- удаление или замена общего `llama.cpp`, который продолжает обслуживать ядро
  и другие сценарии;
- включение GPU-offload;
- изменение пользовательского маршрута литературного описания;
- отдельный OCR-подсценарий для изображений с большим количеством текста;
- публикация, commit, push или сборка установщика.

## 4. Архитектурный контракт

1. Ядро Qwen3 и остальные потребители `llama.cpp` не меняются.
2. Только визуальный аналитик Kimi Среднего комплекта запускается через
   `chatllm.cpp`.
3. AI HUB поднимает `server.exe` на случайном свободном loopback-порту,
   дожидается `/health`, отправляет одно изображение и простой английский
   prompt, получает ответ и гарантированно останавливает процесс.
4. Пользователь никогда не видит сырой Kimi-ответ или reasoning. В ядро
   передаётся только финальная часть ответа после закрытия thinking-блока.
5. Приложение не задаёт `max_tokens`: модель завершает наблюдательный ответ
   самостоятельно.
6. ImageMagick подключается только через локальную runtime-папку процесса и не
   устанавливается глобально в Windows.
7. Старый Kimi-артефакт остаётся в библиотеке и на диске, но больше не входит в
   состав Среднего комплекта. Откат выполняется восстановлением исходных файлов
   кода и карточки комплекта, без повторного скачивания старой модели.

## 5. Критерии приёмки

- Средний комплект показывает Kimi GGMM Q4_1 и считает его отдельным точным
  управляемым артефактом;
- runtime-проверка Kimi использует `chatllm.cpp`, а не `llama.cpp`;
- реальный анализ выбранного изображения выполняется через `chatllm.cpp`;
- ответ читается из фактической структуры API `choices[0].delta.content`;
- thinking-разметка и служебные тайминги не передаются ядру;
- запрос содержит только изображение и простой английский prompt без
  искусственного лимита ответа;
- при отмене или ошибке дочерний server-процесс не остаётся запущенным;
- старые Kimi GGUF/mmproj и пользовательские результаты не удаляются;
- Debug/Release, автоматические тесты, UTF-8 scanner и `git diff --check`
  проходят;
- приложение и установщик не запускаются без отдельной команды пользователя.

## 6. Откат

`H:\AI_HUB\_backups\20260825_chatllm_product_integration`

Локальные runtime/model-файлы нового тракта добавляются в отдельные каталоги и

backup и убрать только новые каталоги `chatllm.cpp` и GGMM Q4_1 после отдельной
проверки их точных путей. Старые Kimi GGUF/mmproj при откате не скачиваются
заново.

## 7. Результат реализации 2026-08-25

- `chatllm.cpp v24` и private portable ImageMagick размещены в отдельном
  продуктовом runtime-каталоге; глобальная установка в Windows не требуется;
- Средний комплект переведён на отдельный управляемый артефакт GGMM Q4_1 с
  точным размером и SHA-256;
- модель в продуктовом каталоге создана как NTFS hardlink уже проверенного
  тестового файла, поэтому дополнительные 10,4 ГБ на диске не заняты;
- runtime-проверка и рабочий анализ используют loopback API `chatllm.cpp`,
  CPU-профиль и гарантированную остановку дочернего процесса;
- reasoning Kimi удаляется на границе backend; ядро получает только финальное
  наблюдение;
- прежние Kimi GGUF/mmproj и общий `llama.cpp` сохранены без изменений;
- продуктовое размещение проверено реальным портретом: корректный ответ получен
  за `34,92` секунды, грубой подмены сцены нет;
- автоматические тесты: `282/282`; Release-сборка: `0` предупреждений и
  `0` ошибок; форматирование, UTF-8 scanner и `git diff --check` пройдены;
- пользовательский сквозной тест подтвердил корректную работу нового visual
  runtime на сложной игровой сцене;
- в `0.1.4-dev` ядро получило роль опытного литературного редактора
  издательства, ясную цель описания изображения и отдельный параметр языка;
  название программы и происхождение черновика из prompt удалены;
- новый контракт ядра разделяет заголовок, абзацы, краткие проверочные детали
  и существенные неопределённости; старый JSON-контракт сохранён для чтения
  прежних сессий;
- версия поднята до `0.1.4-dev`;
- приложение и установщик не запускались, публикация не выполнялась.

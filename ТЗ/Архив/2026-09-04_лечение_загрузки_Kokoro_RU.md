# Лечение загрузки Kokoro RU и сохранение диагностики аварий

Дата: 2026-09-04. Статус: выполнено и принято пользователем, архив.
Версия: 0.1.27-dev. Пользователь провёл один тест, сообщил об отсутствии
ошибок и подтвердил завершение ТЗ. Приёмка фиксирует этот рабочий результат;
длительная статистика редких native crashes не собиралась.
Основание: [исследование](../../Документы_проекта/Диагностика/2026-09-04_Kokoro_RU_исследование_и_кандидат.md).

## Цель и границы

Внедрить проверенный обход избыточного согласования added tokens при загрузке
локального RUAccent turbo3.1. Сохранить токенизацию, фонемы, CPU-режим,
старое исправление token_type_ids и английскую озвучку. Ускорение запуска
подтверждено экспериментом; полное устранение редкого native crash пока не доказано.

Не обновлять зависимости и модели, не менять Heavy, память/очередь его подготовки,
литературные промпты, голос, UI и правила загрузки. Установщик не собирать.

## Реализация

1. Отдельный Python helper, действующий только во время создания RuG2P.
   Проверять точный локальный путь omograph-токенизатора, версии
   transformers 4.41.2 / tokenizers 0.19.1 / ruaccent 1.5.8.3 и SHA-256
   проверенных tokenizer.json, tokenizer_config.json, added_tokens.json.
   Дополнительно сверять наличие и ID всех legacy added tokens в tokenizer.json.
   Только после проверки передавать added_tokens_decoder={}.
2. Для неизвестной версии/содержимого обход пропускать с явной диагностикой;
   оригинальный загрузчик и его ошибки сохранять. Не удалять токены и не
   переписывать файлы пакетов/моделей. Временную подмену всегда восстанавливать.
3. Включить faulthandler у штатного worker. При EOF/обрыве pipe сохранять
   до очистки процесса launcher PID, код выхода в decimal/hex, stderr и
   этап команды. PID настоящего Python писать при старте самого worker.
   Ожидание выхода и stderr ограничить; отмена остаётся отменой.
4. Поднять версию до 0.1.27-dev; обновить каталог лечения и историю.

## Проверки и готовность

- Автотесты границ обхода: другой путь/версия/метаданные, сохранность подмены
  при исключении, сохранение прежнего token_type_ids shim.
- Полное совпадение сериализованного backend токенизатора и контрольных
  токенов/фонем с исследовательским эталоном на установленном комплекте.
- Не менее трёх холодных RU-запусков и двух EN, повторные синтезы;
  WAV 24 kHz mono с ненулевым сигналом, без новых ошибок протокола.
- Проверка диагностики на контролируемом аварийном выходе дочернего процесса
  и обычной Python-ошибке; отмену не выдавать за native crash.
- dotnet restore/build/test, Python-тесты, UTF-8, git diff --check,
  штатный dev-start. Фактический результат каждой проверки записать сюда.
- Пользовательская слуховая/сценарная приёмка и длительное наблюдение остаются
  отдельной границей уверенности; короткую серию не объявлять гарантией.

ТЗ остаётся активным до приёмки. Создание этого ТЗ не запускает архивацию
исследовательского документа, commit или push.

## Результат реализации и проверок

- Обход внедрён в отдельном helper. Три SHA-256 и версии проверяются до
  временной подмены; она применяется только к точному пути без дополнительных
  аргументов. RUAccent.load и AutoTokenizer.from_pretrained восстанавливаются
  даже при исключении. Модели и установленные пакеты не изменялись.
- Штатный worker включает faulthandler и пишет настоящий pythonPid.
  C# при EOF/IOException/уже завершённом процессе дожидается выхода и stderr
  не дольше общей границы 2 с, сохраняет decimal/hex exit code, launcher PID,
  этап и хвост stderr до StopWorker. В метрики добавлено поле diagnostics;
  identity хранится отдельно от хвоста 128 строк по 500 символов.
  Отмена остаётся отменой; поздний stderr старого процесса отбрасывается.
- 345/345 C# тестов, включая контролируемый код 0xc0000005, exit=0 без ответа,
  ограниченное ожидание и отмену. 8/8 Python-тестов: узость обхода, неизвестные
  версии/файлы, несовпадающие IDs, восстановление метода, старый shim и
  структурированная Python-ошибка с продолжением обработки следующей команды.
- Шесть прямых запусков штатного worker: 3 RU / 12 синтезов и 3 EN / 6 синтезов.
  Все exit=0; все 18 WAV — 24 kHz mono PCM16 с ненулевым сигналом.
  RU cold load 11,171–12,281 с, EN 3,375–3,782 с. В исходных контролях RU
  ~25–26 с; разницу нагрузки CPU между сериями не выдавать за точный benchmark.
- Backend SHA-256 совпал с эталоном полностью:
  00911401812289c0ab07df113db2c04a1c60ad9d475215cc275f28e8b5d5b99a.
  Все IDs/masks/offsets шести фраз и фонемы двух прежних сводок совпали.
  Повторный load вернул alreadyLoaded/0; shim сохранился на accent_model
  и stress_usage_predictor, которым ONNX действительно требует token_type_ids.
- В ходе написания проверочного скрипта исправлены две ошибки самого теста:
  неверное ожидание shim на omograph_model и сравнение tuple offsets с JSON
  lists. Финальная проверка проходит; это не изменения модели или произношения.
- dotnet restore, Release build/test и штатный start-aihub.ps1 (Debug build)
  успешны, 0 ошибок/предупреждений сборки. Окно AI HUB 0.1.27-dev отвечает.
  Новый helper скопирован в Debug/Release, SHA-256 совпал с исходником.
  py_compile, UTF-8/scanner по изменённым файлам и diff --check пройдены.
  Новых UI-строк нет. Предупреждения torch dropout/weight_norm остались
  прежними, зависимости не обновлялись. Установщик не пересобирался по правилу.

Локальные доказательства: Тесты/Kokoro_treatment_20260904/production,
production_summary.json, equivalence.json. Сырые сводки/WAV не публиковались.
Новые проверочные инструменты: Инструменты/tests/test_kokoro_ru_tokenizer_compat.py
и verify_kokoro_treatment.py. Старый диагностический wrapper адаптирован

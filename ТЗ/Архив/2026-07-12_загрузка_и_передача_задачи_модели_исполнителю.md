# ТЗ: загрузка и передача задачи модели-исполнителю

Дата начала: 2026-07-12
Статус: выполнено и подтверждено пользовательским сквозным тестом 2026-07-14

## Уточнение 2026-07-14: доверенный пул кандидатов

После проверки живого журнала граница ответственности изменена:

- программа получает inventory и результаты каталога, нормализует model/repo/GGUF как одну сущность и определяет семейство;
- программа отвечает только за факты: installed/runnable, backend, формат, совместимость с ПК, нагрузочный профиль и допустимость политики;
- скачиваемая альтернатива обязана относиться к другому семейству относительно выбранной установленной модели;
- одинаковые веса в основном репозитории и GGUF-упаковке не могут образовать пару;
- ядро получает компактный доверенный пул с короткими ID и описанием требуемых capability-протоколов;
- ядро выбирает установленный ID, альтернативный ID, предпочтительный ID и формулирует плюсы, ограничения и причины;
- ядро больше не переписывает repo, status, family, role и capability class из результатов инструментов;
- если установленной модели достаточно, она может быть предпочтительной, но альтернатива другого семейства всё равно показывается;
- обязательные технические tool-вызовы и защита от их точного повтора контролируются программой;
- финальную карточку программа собирает из доверенных фактов и смыслового решения ядра.

## 1. Цель

Довести «Режим неопределенности» от финальной карточки задачи до первого результата более мощной локальной модели-исполнителя.

После подготовки карточки ядро должно выбрать исполнителя, а программа — проверить его наличие, при необходимости предложить безопасную загрузку конкретного совместимого GGUF-файла, запустить отдельную сессию исполнителя и передать ему работу.

Сценарий остается технологической песочницей. Первый проход должен быть сквозным и проверяемым, но не обязан сразу поддерживать все типы моделей и backends.

## 2. Принцип ролей

Ядро:

- опрашивает пользователя;
- строит capability profile и карточку задачи;
- выбирает модель-исполнителя по коротким ID из проверенного программой пула;
- объясняет преимущества, ограничения и предпочтение двух вариантов;
- не скачивает файлы самостоятельно;
- не переписывает качественный ответ более сильной модели.

Модель-исполнитель:

- получает готовую карточку и prompt;
- выполняет основную интеллектуальную работу;
- использует только разрешенные инструменты;
- возвращает результат или структурированный запрос уточнения;
- не выбирает другую модель вместо себя.

Программа:

- сама получает inventory, каталог и при необходимости результаты живого поиска;
- формирует доверенный пул совместимых кандидатов и обеспечивает другое семейство альтернативы;
- разрешает выбранную модель в конкретный артефакт;
- проверяет ПК, место, источник и формат;
- требует подтверждение перед сетью и загрузкой;
- скачивает, проверяет и регистрирует модель;
- управляет runtime, контекстом, отменой и журналами.

## 3. Граница первого этапа

Поддерживаются:

- текстовые модели;
- GGUF;
- backend `llama.cpp`;
- один исполнитель на задачу;
- один активный executor runtime;
- загрузка только после явного подтверждения пользователя;
- отмена и повтор после ошибки;
- использование уже установленной подходящей модели без повторной загрузки.

Не входят:

- автоматическая установка неизвестных backends;
- мультимодальные модели;
- параллельная команда исполнителей;
- полноценный marketplace;
- универсальный UI всех будущих сценариев.

## 4. Разрешение артефакта

Выбранный `repoId` должен быть преобразован в конкретный исполняемый файл:

```text
model repo -> compatible GGUF repository/file -> quant -> size -> source -> llama.cpp
```

Приоритет первого этапа:

1. Уже установленный точный исполнитель.
2. Уже установленный совместимый артефакт выбранной модели.
3. GGUF-файл из подтвержденного каталожного источника.
4. Явная ошибка без скрытой подмены модели.

Программа не должна самовольно выбирать другое семейство вместо решения ядра.

## 5. Установка

До загрузки показываются:

- название модели;
- repository и имя файла;
- квант;
- размер;
- ожидаемое размещение;
- источник;
- лицензия, если она известна;
- оценка совместимости с ПК.

Загрузка:

- начинается только после подтверждения;
- поддерживает прогресс и отмену;
- пишет во временный файл;
- проверяет ожидаемый размер и SHA-256, если он доступен;
- до полной загрузки читает GGUF metadata и отклоняет вспомогательные MTP/draft/adapter/projector-артефакты;
- атомарно переносит готовый файл;
- создает локальный manifest;
- присваивает статус `installed` только после реального запуска и health-check в текущем `llama-server`;
- сохраняет `runtime_incompatible` и точную причину, если backend не смог загрузить модель;
- не оставляет неполный файл зарегистрированным как модель.

Автотесты не должны скачивать реальные AI-модели. Сетевой контур проверяется подмененным локальным источником и маленькими искусственными файлами.

## 6. Передача задачи

Исполнитель получает отдельный пакет с явным происхождением данных:

- `programFacts` — подтверждённые программой сведения о ПК, настройках и доступных возможностях;
- `userSignals` — исходные выборы пользователя без усиленной интерпретации;
- `coreHypotheses` — предварительные выводы ядра с пометкой, что это только фон и не готовая постановка;
- `capabilityProfile` — требуемые классы возможностей;
- `unknowns` — то, что ядро намеренно оставило выяснять исполнителю;
- правила интернета, приватности и доступные инструменты;
- язык и предпочтения ответа.

Ядро определяет подходящий класс модели, но не обязано знать предметную тему и не формулирует вымышленную «готовую задачу». Полная история опроса не передаётся, однако исходные выборы пользователя сохраняются отдельно от интерпретаций ядра.

## 7. Сессия и контекст исполнителя

Исполнитель использует долгоживущую сессию:

- модель загружается в RAM/VRAM один раз;
- runtime не перезапускается после каждого ответа;
- рабочий контекст накапливается;
- сжатие запускается примерно при 80% доступной рабочей области;
- после сжатия runtime остается загруженным;
- полный сырой журнал сохраняется отдельно.

Контрольная точка содержит цель, решения, факты, источники, результаты инструментов, артефакты, текущий план, незавершенные действия и риски.

В первом сквозном проходе допускается одна генерация результата без фактического достижения порога 80%, но архитектура и тесты бюджета контекста должны быть заложены сразу.

## 8. Собственное сужение исполнителя

После передачи управление переходит исполнителю. Он начинает с широкого предположения о направлении и самостоятельно сужает реальную задачу пользователя. Для этого используется повторяемый контракт:

```json
{
  "status": "clarification_step",
  "thought": "Коротко объясняю, что уточняю и почему.",
  "question": "Какой период нужно анализировать?",
  "options": ["Месяц", "Год", "Все время"],
  "allowCustom": true
}
```

Правила:

- от 2 до 6 коротких вариантов и отдельный «Свой вариант»;
- уточнения могут повторяться столько раз, сколько действительно требуется;
- предметные ответы возвращаются прямо исполнителю, без повторного участия ядра;
- естественный текст, похожий на уточнение, не считается финальным результатом: программа выполняет repair структурированного контракта;
- финал допустим только после явного статуса `final_result`;
- пользователь может завершить сессию отдельной кнопкой рядом с управлением звуком.

## 9. Результат

Исполнитель возвращает явный статус `final_result`, основной результат, источники, созданные файлы, предупреждения и незавершенные пункты. Статус `cannot_continue` используется для честной остановки, когда работа невозможна.

Программа проверяет техническую целостность. Ядро вмешивается только при явной незавершенности или несоответствии карточке задачи.

## 10. Поток и Matrix-анимация

Генерация ядра и исполнителя переводится на потоковую выдачу там, где это поддерживает runtime.

Один поток используется независимо двумя потребителями:

```text
token stream -> full response buffer
             -> Matrix activity feed
```

Текстовые статусы остаются существующими. Дополнительно центральная рабочая область показывает крупную сцену активности примерно на половину окна.

Правила Matrix-дождя:

- до первого токена идет редкий фоновый дождь;
- реальные символы ответа используются без исправления содержания;
- внимательный пользователь может заметить слова, JSON и фрагменты ответа;
- системный prompt, backend logs и пути к файлам в визуализатор не передаются;
- поток ограничивается очередью, UI обновляется пакетно;
- при repair дождь не исчезает;
- после проверки ответа сцена затихает;
- отмена остается доступной.

Компонент должен быть общим для ядра и исполнителя, но не встраивать бизнес-логику в `MainWindow`.

## 11. Журналы

У сценария сохраняется существующий журнал ядра. Для исполнителя создается отдельный JSONL-журнал внутри папки сценария с записями:

- выбранная модель и артефакт;
- запрос подтверждения;
- загрузка, проверка и регистрация;
- запуск и остановка runtime;
- пакет передачи задачи;
- контрольные точки контекста;
- уточнения;
- сырой ответ и итог;
- ошибки и отмена.

Отдельно записываются происхождение элементов handoff, каждый шаг уточнения, ответы пользователя, repair контракта, голос исполнителя и ручное завершение сессии.

Секреты и скрытые системные пути в пользовательский результат не выводятся.

## 12. Критерии готовности

Первый этап готов, если:

1. Финальная карточка предлагает продолжить с выбранным исполнителем.
2. Установленная модель находится без повторной загрузки.
3. Для отсутствующей модели формируется конкретный проверяемый план загрузки и запрашивается подтверждение.
4. Отмена не регистрирует неполный файл как готовую модель.
5. Исполнитель запускается отдельной долгоживущей сессией.
6. Карточка и prompt передаются исполнителю.
7. Поток ответа питает крупную Matrix-анимацию.
8. Полный ответ собирается и показывается после завершения.
9. Журналы ядра и исполнителя разделены.
10. Автотесты не скачивают реальные модели.
11. Вспомогательный GGUF не может быть выбран как основные веса.
12. Модель без успешного runtime health-check не попадает в runnable inventory.
13. Ядро передаёт гипотезу направления как фон, а не как готовую предметную задачу.
14. Исполнитель может провести несколько собственных шагов сужения и принять свой вариант пользователя.
15. Обычная проза с вопросом не помечается как успешный финал.
16. Кнопка завершения останавливает генерацию, голос и runtime и фиксирует причину в журнале.
17. Реплики исполнителя озвучиваются RHVoice-профилями `Elena` (русский) и `BDL` (английский), с безопасным fallback.
18. Финал содержит ровно два подтверждённых варианта: установленный runnable и отсутствующий для загрузки; пользователь видит их преимущества и ограничения и сам выбирает исполнителя.
19. Ядро выбирает только доверенные ID и не обязано воспроизводить технические сведения о моделях.
20. Установленный кандидат может быть рекомендован как достаточный; загружаемый вариант не получает автоматического приоритета.

## 16. Реализация доверенного пула 0.0.56-dev

- `ChoiceExecutorCandidatePoolService` получает структурированный inventory и локальный каталог без участия ядра;
- живой Hugging Face fallback включается только при отсутствии валидной пары в локальных данных;
- программа отбрасывает неподходящие по режиму нагрузки, ПК и политике варианты и определяет широкое семейство модели;
- финальный JSON-контракт ядра содержит только `installedCandidateId`, `alternativeCandidateId`, `preferredCandidateId` и две смысловые оценки;
- технические поля карточки и реальные модели восстанавливаются программой из доверенного пула;
- модельные tools скрыты от ядра, точные повторные web-вызовы блокируются;
- repair получает компактный пул повторно, но не длинные сырые выдачи инструментов;
- добавлены тесты выбора установленного победителя, альтернативы другого семейства и запрета неизвестных ID.

## 15. Голос исполнителя

- Озвучка относится к роли исполнителя только внутри «Режима неопределённости».
- Русский профиль: RHVoice `Elena`; английский профиль: RHVoice `BDL`.
- Ядро продолжает использовать общие профили `Aleksandr` и `SLT` во всех сценариях.
- В инструментах других сценариев профили `Aleksandr`, `SLT`, `Elena` и `BDL` запрещены без прямой просьбы пользователя.
- При отсутствии `Elena` или `BDL` сценарий не ломается: используется доступный RHVoice-профиль соответствующего языка, затем eSpeak.
- Озвучиваются короткая мысль и вопрос шага; длинный финальный результат автоматически не читается.

## 13. Проверки

- unit tests разрешителя артефакта, installer manifest и контекстного бюджета;
- fake/local HTTP download без реальных моделей;
- streaming parser и ограниченная очередь анимации;
- Debug/Release build без новых предупреждений;
- полный test suite;
- локализация RU/EN;
- UTF-8/Cyrillic scanner;
- publish smoke без новых моделей в артефакте;
- ручная проверка UI пользователем после внутренних тестов Codex.

Добавлено в `0.0.54-dev`:

- задача ядра закреплена как подбор класса модели, а не выдумывание отсутствующей предметной постановки;
- исполнитель получил собственный повторяемый контракт `clarification_step / final_result / cannot_continue`;
- нарушение JSON-контракта запускает repair и больше не превращает обычный вопрос в ложный успешный финал;
- добавлены несколько последовательных шагов исполнителя, до шести вариантов и свободный ответ;
- добавлена кнопка ручного завершения, которая останавливает генерацию, голос и runtime;
- реплики исполнителя озвучиваются отдельными RHVoice-профилями `Elena / Bdl`; ядро сохраняет `Aleksandr / Slt`;
- официальный setup-скрипт расширен закреплёнными SHA-256 новых голосов;
- живой backend smoke на уже установленной Qwen3.6 27B подтвердил строгий JSON Schema без загрузки новых моделей.

Добавлено в `0.0.55-dev`:

- ядро обязано предложить ровно двух исполнителей: одного уже установленного и runnable, второго отсутствующего и доступного для загрузки;
- обе модели должны быть подтверждены результатами инструментов и проходить общую политику мощности, lineage и совместимости с ПК;
- модели не могут совпадать, а статус нельзя определять только со слов ядра;
- для каждого варианта ядро формулирует преимущество, ограничение и причину соответствия профилю;
- финальная страница показывает две кнопки сравнения и не начинает подготовку исполнителя до явного выбора пользователя;
- `recommendedExecutor` остаётся предварительным предпочтением ядра, но не подменяет выбор пользователя;
- если корректную пару собрать невозможно, финал не считается валидным и проходит repair вместо молчаливого возврата к одной модели.
- repair запоминает только фактически ошибочного кандидата и не запрещает одновременно второй, уже подтверждённый вариант;
- после выбора пользователя именно выбранная карточка становится источником модели, роли и причины для resolver/handoff.
- внутренние проверки: Debug/Release без предупреждений, 79/79 тестов, format check, scanner `211` файлов, локализации `415/415` и publish-smoke без моделей;

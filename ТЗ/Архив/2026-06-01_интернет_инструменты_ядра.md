# ТЗ: интернет-инструменты ядра

Дата: 2026-06-01

## Цель

Доказать, что ядро AI HUB может пользоваться интернет-инструментами программы:

- искать актуальную информацию;
- читать web-страницы;
- скачивать файл по прямой ссылке;
- сохранять действия инструментов в JSONL;
- получать результат обратно как служебный контекст.

## Контекст концепции

AI HUB не является прямым чатом. По исходной идее ядро — диспетчер программы:

- понимает задачу;
- выбирает ветку сценария;
- подбирает модели и инструменты;
- вызывает web-инструменты;
- анализирует результат;
- ведёт пользователя через кнопочное дерево решений.

Модель не должна сама напрямую владеть сетью. В сеть ходят инструменты AI HUB, а ядро получает результат.

## Реализация первого слоя

Добавить минимальный Tool Gateway:

- принимает служебные команды;
- вызывает нужный инструмент;
- возвращает текстовый результат;
- пишет события в JSONL.

Добавить инструменты:

1. `WebSearchTool`
   - команда для проверки: `web_search: запрос`;
   - первый dev-провайдер без API-ключа: DuckDuckGo Lite HTML-поиск;
   - архитектурно оставить путь к будущим провайдерам SearXNG/Brave Search API.

2. `WebPageReaderTool`
   - команда для проверки: `web_read: url`;
   - скачивает HTML;
   - вырезает `script/style`;
   - извлекает `title` и читаемый текст;
   - ограничивает объём текста для передачи ядру.

3. `WebDownloadTool`
   - команда для проверки: `web_download: url`;
   - скачивает файл;
   - сохраняет его в папку web-загрузок;
   - считает размер и SHA-256;
   - показывает визуальный прогресс в F12-окне при длительном скачивании;
   - определяет тип ответа по `Content-Type`;
   - добавляет расширение файла по типу ответа, если URL без расширения;
   - предупреждает ядро, если скачана HTML-страница вместо прямого файла/картинки;
   - не запускает скачанный файл.

## Хранение

Если настроена папка результатов:

```text
<Папка результатов>\AI_HUB\Tools\Web\
  Search\
  Pages\
  Downloads\
```

Если папка результатов не настроена:

```text
Runtime\Tools\Web\
  Search\
  Pages\
  Downloads\
```

## Debug-проверка

В `F12` debug-окне добавить временные команды:

```text
web_search: qwen3 gguf license
web_read: https://example.com
web_download: https://example.com/file.txt
core_tool_test: найди и скачай маленькую Qwen GGUF-модель для проверки
```

Это не финальный пользовательский UI, а лаборатория для проверки живого инструментального контура.

Дополнительно:

- ручные `web_*` команды проверяют сами инструменты;
- `core_tool_test:` проверяет, что ядро может запросить tool-команду, получить результат и продолжить сценарий.
- обычный prompt в F12 debug-окне должен идти через ядро с доступными инструментами: модель сама решает, отвечать сразу через `FINAL:` или запросить `web_search`, `web_read`, `web_download`.

## Логирование

В JSONL писать:

- `tool_request`;
- `tool_result`;
- `tool_error`;
- запрос;
- URL;
- путь сохранения;
- размер;
- SHA-256;
- краткую сводку результата.

## Ограничения первого слоя

- Не загружать файлы наружу.
- Не авторизоваться на сайтах.
- Не управлять браузером.
- Не запускать скачанные файлы.
- Не обходить Windows Defender.
- Не делать полноценный UI дерева решений.
- Не индексировать найденное в RAG.

## Фактический результат проверки

- Ручные smoke-test команды Codex скачали первые два файла `Qwen3-0.6B-Q4_K_M.gguf` в `Tools\Web\Downloads` для проверки инструмента.
- Сценарий `core_tool_test` подтвердил, что ядро Qwen3 8B само запросило команду `web_download:`; AI HUB выполнил её и скачал третий файл с временем `03:47`.
- Пользователь заметил отсутствие визуального статуса скачивания; добавлен progress UI в debug-окне.
- Пользователь уточнил, что в debug-режиме должны быть все доступные ядру возможности; обычные сообщения F12-окна теперь тоже проходят через инструментальный контур.
- Smoke-test обычного prompt-а с прямой ссылкой `https://example.com/` подтвердил вызов `web_download` и сохранение `download.bin`.
- После теста с котиком выяснилось, что ядро скачало HTML-страницу поиска Яндекс.Картинок вместо изображения. Добавлена типизация скачивания: `Content-Kind`, автодобавление расширения и предупреждение для HTML, чтобы ядро продолжало искать прямую ссылку на картинку.
- После тестов с разными типами файлов выяснилось, что модель иногда отвечает `нет доступа`, хотя инструменты доступны. Добавлен recovery: если на первом шаге debug-ядро отказывается из-за отсутствия доступа, AI HUB сам запускает `web_search` по запросу пользователя и возвращает результат ядру.
- Ошибки инструментов вроде `403 Forbidden` больше не должны обрывать цепочку: Tool Gateway возвращает их ядру как текстовый `Tool error` с подсказкой попробовать другой источник.
- Проверены разные типы прямых загрузок: HTML, JSON, TXT, PNG, JPEG, PDF, MP3. Для них выставляется `Content-Kind`, а расширение добавляется по `Content-Type`, если URL был без расширения.
- По уточнению пользователя расширен сценарий выбора источников: ядро не должно ограничиваться первым сайтом. `web_search` отдаёт до 10 результатов, а agent-loop F12 допускает до 10 tool-запросов на пользовательскую задачу. После неудачного источника, HTML вместо файла, ошибки или сомнительного результата ядро получает инструкцию пробовать следующий источник и выбирать лучший итог.
- По проверке пользователя выявлено: ядро могло написать, что файл найден/сохранён, хотя фактически выполнялись только `web_search`, а `web_download` не запускался. Добавлен guard для запросов на скачивание: финальный ответ без подтверждения `Web download complete` не принимается; AI HUB возвращает ядро к поиску прямой ссылки или честно сообщает, что файл не скачан после лимита.
- Следующая проверка показала, что ядро на прямой `.jpg`-ссылке вызывало `web_read`, а не `web_download`. Добавлен автоперехват: для задач скачивания `web_read` по прямому файловому URL (`jpg/png/mp3/pdf/gguf/...`) автоматически выполняется как `web_download`.
- `web_read` усилен: теперь отдаёт не только текст страницы, но и найденные кандидаты прямых файлов из `href/src/srcset/content`. Это помогает ядру читать страницу-источник, увидеть реальные `jpg/png/mp3/pdf/...` ссылки и потом скачать одну из них.
- По обсуждению качества поиска принято, что reranker лучше подключать отдельной специализированной моделью, а не нагружать основное ядро. В код добавлена авто-загрузка `BAAI/bge-reranker-v2-m3` сразу после основного Qwen3 8B: модель скачивается в папку моделей `Tools/Reranker/BAAI-bge-reranker-v2-m3`, получает `tool-model.json`, проверяется по размеру и SHA-256 там, где Hugging Face отдаёт hash.
- На этом шаге reranker только скачивается и регистрируется. К логике web-поиска он пока не подключён.
- F12 discovery видит служебные tool-модели, но показывает их как `tool-only`: их нельзя выбрать и запустить как чат-модель.
- Версия повышена до `0.0.31-dev`.
- После подтверждения пользователя reranker подключён к логике `web_search`: результаты DuckDuckGo Lite теперь проходят через `WebSearchRerankerService`, который вызывает локальный Python/Transformers backend с `BAAI/bge-reranker-v2-m3`.
- Для dev-проверки создано локальное venv-окружение `Runtime/Python/reranker/.venv` с пакетами `torch`, `transformers`, `safetensors`. Это runtime-папка, она не публикуется в GitHub и не входит в установщик.
- Если Python runtime, скрипт или модель недоступны, поиск не падает: включается `lexical-fallback`, а результат содержит строку `Rerank: ...` с объяснением режима.
- Добавлен скрипт `Исходники/AIHub/Tools/bge_rerank.py`, который принимает JSON через stdin и возвращает оценки релевантности.
- Версия повышена до `0.0.32-dev`.

# ТЗ: подключение локального каталога моделей как инструмента ядра

Дата: 2026-07-11
Статус: завершено и подтверждено пользовательской проверкой

## Цель

Подключить накопительный каталог Hugging Face к «Режиму неопределенности» через отдельный structured tool. Каталог не является частью ядра, его личности или постоянного prompt-контекста.

## Граница ответственности

- Каталог хранится и обновляется отдельными сервисами.
- Ядро не читает `catalog.json` напрямую и не управляет синхронизацией.
- Ядро вызывает `model_catalog_search` со структурированными требованиями.
- Инструмент возвращает не более шести проверяемых кандидатов и причины совпадения.
- Инструмент не назначает финальную модель. Сравнение кандидатов и выбор выполняет ядро.
- Полный каталог не помещается в prompt; в контекст попадает только компактный результат одного вызова.
- `hf_find_model` сохраняется как живой интернет-поиск для расширения или актуальной проверки, когда локальных данных недостаточно.
- Скачивание и запуск моделей этим ТЗ не выполняются.

## Контракт инструмента

Вход:

- одно или несколько направлений каталога;
- тип задачи;
- требуемые возможности;
- допустимый уровень нагрузки (`light`, `optimal`, `extreme`, `any`);
- максимальное число результатов от 1 до 6.

Выход:

- состояние локального каталога и дата последней успешной синхронизации;
- число рассмотренных записей;
- список кандидатов с точным `repoId`, параметрами, pipeline, лицензией, направлениями, уровнями нагрузки, источником записи и краткими причинами совпадения;
- явный признак, достаточно ли локальных кандидатов или нужен запасной живой поиск;
- отсутствие поля с программно выбранным победителем.

## Правила подбора

- Исключать недоступные, private и disabled записи.
- Учитывать совпадение направлений, ролей, pipeline, тегов и capability-запроса.
- Учитывать выбранный пользователем режим нагрузки и размер модели.
- Не вводить предпочтение конкретному издателю или семейству.
- Популярность, свежесть и полноту метаданных использовать только как дополнительные признаки.
- Ручные исключения меньше 8B допустимы только в лёгком режиме; общая политика сценария по запрету слабого исполнителя остаётся отдельной финальной проверкой.

## Оркестрация сценария

1. Перед финалом ядро обязательно проверяет `inventory`.
2. Затем ядро обязательно вызывает `model_catalog_search`.
3. Если каталог отсутствует, повреждён или не дал кандидатов, ядро вызывает `hf_find_model`.
4. Если локальные кандидаты есть, ядро вправе вызвать `hf_find_model` для актуальной проверки, но это не обязательно для офлайн-финала.
5. Финальная модель должна точно присутствовать в evidence одного из инструментов поиска моделей.
6. `current_core` допустим только по уже действующей политике fallback.

## Проверки готовности

- Unit-тесты контракта, фильтрации, лимита, отсутствующего каталога и отсутствия программного победителя.
- Тест точной проверки модели из результата локального каталога.
- Debug/Release build, полный набор тестов, format/scanner/localization checks и smoke-запуск.
- Обновление версии и проектной истории.

## Результат реализации

- Добавлены отдельные модели ответа и `LocalModelCatalogTool`.
- Новый tool зарегистрирован в сценарном каталоге и общем Tool Gateway с журналированием.
- Финальная оркестрация использует последовательность `inventory → model_catalog_search → при необходимости hf_find_model`.
- Локальный живой прогон вернул 6 кандидатов для научно-текстового профиля без программного выбора победителя.
- Пройдены 40/40 тестов, Debug/Release build без предупреждений, format check, scanner `316` файлов, локализации `353/353`, `git diff --check` и smoke-запуск.
- Установщик не пересобирался; commit/push не выполнялись.

## Исправление по пользовательскому прогону

- Журнал `2026-07-11_13-35-47_uncertainty_*.jsonl` подтвердил исправную выдачу локального каталога: 3 кандидата 30–32B.
- Безопасные смысловые aliases `context_volume → context_window`, `executorRole → model_class` и `data_analyst → specialist_model` нормализуются до проверки.
- Repair запоминает отклонённые модели и прямо запрещает повторять их, не назначая альтернативу программно.
- Текст ошибки поясняет, что на экране сохранён предыдущий шаг, а проверку не прошёл следующий ответ ядра.
- После исправления пройдены 42/42 теста, Debug/Release build без предупреждений, format check, scanner `318` файлов, локализации `353/353`, `git diff --check` и smoke-запуск.

## Расширение после гибридной приёмки

- рассчитывать для кандидата ориентировочную память Q4 и проверять физическую совместимость с RAM/VRAM из паспорта ПК;
- не возвращать заведомо неподходящие ПК кандидаты и повторно проверять выбранного исполнителя перед финалом;
- определять родство и поколение по `baseModels`/metadata каталога, используя имя только как fallback для живой выдачи;
- отклонять противоречивые финальные карточки, например `needsWeb=false` вместе с web-инструментами;
- автоматически обновлять накопительный каталог в фоне при запуске, не блокируя UI и не уничтожая прежнюю базу при сетевой ошибке.

## Результат расширения

- Добавлена консервативная оценка Q4: вес 4-bit плюс 20% runtime-overhead, отдельные бюджеты RAM/VRAM для light/balanced/extreme и проверка свободного диска.
- Заведомо неподходящие ПК модели исключаются из локальной выдачи; выбранный исполнитель повторно оценивается перед финальной карточкой.
- `baseModels` имеет приоритет для lineage; при его отсутствии используются `modelType` и repo metadata, а имя остаётся fallback живой выдачи.
- Локальная выдача заранее исключает семейство текущего ядра без значительного перехода поколения, не назначая победителя.
- Валидатор запрещает `needsWeb=false` вместе с web-инструментами и web при `no_external_data`, `offline_only` или `local_only`.
- Фоновый startup-сервис проверяет свежесть каталога, обновляет его не чаще одного раза в 24 часа и сохраняет прежнюю базу при полном сетевом отказе.
- На паспорте тестового ПК 32B проходит как GPU-fit, 120B как hybrid-fit, а сверхкрупные модели, не помещающиеся даже в Q4, исключаются.
- Проверки: 54/54 теста, Debug/Release и CatalogProbe Release build без предупреждений, format check, scanner `324` файлов, локализации `353/353`, bundled seed, `git diff --check` и smoke-запуск.
- Smoke-журнал подтвердил startup-ветку `skipped_fresh`; окно не блокировалось и сетевой обход свежей базы не запускался.

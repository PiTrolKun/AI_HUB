# ТЗ: стратегический web research для ядра

## Цель

Улучшить интернет-поиск AI HUB так, чтобы локальная модель не придумывала поисковую стратегию сама.

Добавить Codex-подобный инструментальный слой `web_research: запрос`, который:

- строит несколько нормальных вариантов поискового запроса;
- запускает поиск по этим вариантам;
- диагностирует пустую выдачу;
- читает 1-3 наиболее подходящие страницы через существующий `web_read`;
- возвращает модели структурированную таблицу фактов, источников и проблем.

## Причина

Текущий `web_search` технически работает, но маленькая локальная модель строит слабую стратегию:

- повторяет похожие запросы;
- использует плохие конструкции вроде `site:nasa.gov OR site:esa.int OR ...`;
- при `HTTP 202` от DuckDuckGo не понимает, что проблема может быть в провайдере;
- без отдельного контура может остановиться на нуле или поверхностном результате.

## Что входит

- Новый сервис `SearchStrategyService`.
- Новые модели результата research:
  - поисковые попытки;
  - выбранные источники;
  - прочитанные страницы;
  - диагностика;
  - сохранённый JSON.
- Новый инструмент Tool Gateway:

```text
web_research: пользовательский запрос
```

- Обновление F12 prompt-а: для актуальных фактов, новостей и проверяемой информации сначала предпочитать `web_research`, а не одиночный `web_search`.
- Сохранение результата в:

```text
<Папка результатов>\AI_HUB\Tools\Web\Research
```

## Стратегия поиска

Для одного пользовательского запроса инструмент должен сам создать несколько вариантов:

- исходный запрос;
- упрощённый запрос;
- английский вариант для типовых тем;
- вариант без жёсткого периода;
- вариант с `official` / `официально`, если запрос похож на поиск официального источника;
- для новостей: варианты с `news`, `latest`, `Reuters`, `BBC`, `NASA`, `ESA`, `Space.com` по смыслу запроса.

На этом этапе не нужна идеальная лингвистика. Достаточно простого эвристического генератора, который заметно лучше случайных запросов модели.

## Чтение источников

Если поиск дал результаты:

- выбрать до 3 лучших уникальных URL;
- не читать страницы поиска и очевидные агрегаторы, если есть более прямые источники;
- прочитать страницы через существующий `WebPageReaderTool`;
- ошибки чтения не должны ломать весь research, а должны попадать в диагностику.

## Диагностика

Если все попытки поиска дали ноль:

- явно вернуть `Confirmed sources: 0`;
- указать вероятную причину:
  - provider blocked/challenged;
  - provider empty/parser mismatch;
  - query too narrow;
  - no confirmed event found;
- запретить модели говорить, что факты найдены.

Если часть попыток дала результаты, но страницы не удалось прочитать:

- вернуть найденные URL;
- указать, что подтверждённого текста страниц нет;
- запретить уверенный пересказ без прочитанного источника.

## Что не входит

- Боевой UI для research.
- Покупные/ключевые API поиска.
- Скачивание файлов.
- Автоматическое выполнение действий по результатам поиска.
- Полная RAG-память.
- Замена `web_search`; старый инструмент остаётся для низкоуровневой отладки.

## Критерии приёмки

- В F12 доступна команда `web_research:`.
- Модель получает не сырые поисковые обрывки, а подготовленный research-результат.
- При пустой выдаче результат честно объясняет причину и не разрешает выдумывать факты.
- При успешной выдаче инструмент читает подходящие страницы или явно пишет, почему это не удалось.
- Код не превращает `DebugChatWindow.xaml.cs` или `ToolGateway.cs` в новый монолит сверх необходимого.

## Дополнение: датированные пункты и рассуждение ядра

После пользовательской проверки выявлено: модель может брать из preview страницы меню, навигацию или общие слова и выдавать это как новость.

Нужно добавить:

- извлечение датированных фрагментов из прочитанных страниц;
- отдельный блок `Dated items` в ответе `web_research`;
- правило для F12: при новостном ответе использовать `Dated items` как основу, а не общий preview;
- правило для ядра: после подтверждённых фактов можно добавлять собственное краткое рассуждение, но явно не смешивать его с найденными фактами.

# ИДЕЯ: модульный локальный голосовой backend для AI_HUB

**Дата фиксации идеи:** 2026-07-12
**Дата изучения официальной документации:** 2026-07-12
**Статус:** идея на будущее, не активное ТЗ
**Назначение файла:** сохранить архитектурную концепцию для последующего изучения и возможной реализации в Codex. Перед началом работ обязательно повторно проверить актуальность проектов, лицензий, API, форматов моделей и поддерживаемых языков.

---

## 1. Причина появления идеи

AI_HUB уже имеет два лёгких системных голоса ядра:

- eSpeak NG как характерный ретро-голос;
- RHVoice как более разборчивая альтернатива.

Для модели-исполнителя нужен другой класс озвучки:

- более естественный голос;
- один постоянный узнаваемый тембр;
- мягкое изменение характера речи между сценариями;
- отсутствие необходимости хранить отдельную TTS-модель для каждого сценария;
- работа на среднем игровом ПК;
- отсутствие конкуренции с текстовой моделью за VRAM;
- загрузка тяжёлых весов только по необходимости;
- полное освобождение памяти после периода бездействия.

Целевой компьютер нельзя оценивать по основному ПК разработчика. Ориентир проекта:

- Windows 11;
- современный средний игровой CPU;
- 16–32 ГБ RAM;
- видеокарта уровня RTX 3060 / RTX 4060 или близкая;
- текстовая модель-исполнитель может уже занимать основную VRAM и часть RAM.

Из пользовательского теста на RTX 4090 видно, что исполнитель Qwen 27B Q4 практически заполняет 24 ГБ VRAM. Поэтому базовый голосовой backend должен работать на CPU и не рассчитывать на свободную видеопамять.

---

## 2. Главная идея

Не обучать полноценный TTS с нуля и не встраивать один тяжёлый сторонний проект непосредственно в WPF-приложение.

Вместо этого создать собственный модульный голосовой backend AI_HUB, собранный как конструктор из независимых компонентов:

```text
текст исполнителя
→ нормализация текста AI_HUB
→ разметка речевого смысла и стиля
→ фонемизация / G2P
→ компактная акустическая модель
→ вокодер или модель прямого waveform
→ DSP-постобработка
→ поток PCM
→ воспроизведение
```

Ценность решения должна находиться не в написании нового вокодера, а в собственных:

- контрактах между компонентами;
- речевых профилях сценариев;
- нормализации технического текста;
- управлении ресурсами;
- разделении постоянного runtime и загружаемых весов;
- интеграции голоса с логикой AI_HUB.

---

## 3. Формат самостоятельной headless-утилиты

Голосовой элемент следует реализовывать отдельно от основного приложения, без собственного визуального интерфейса.

Предлагаемая схема:

```text
AI_HUB.exe
    │
    └── Named Pipes / локальный IPC
            │
            └── AIHub.VoiceHost.exe
                    │
                    └── AIHub.TtsWorker.exe
```

### `AIHub.VoiceHost.exe`

Постоянный лёгкий процесс:

- принимает команды от AI_HUB;
- хранит очередь реплик;
- поддерживает IPC;
- выполняет разбиение текста;
- применяет речевой профиль сценария;
- управляет аудиовыводом;
- держит только лёгкие общие компоненты;
- запускает и останавливает модельный worker;
- контролирует TTL;
- возвращает состояния, ошибки и прогресс;
- не содержит UI.

### `AIHub.TtsWorker.exe`

Временный тяжёлый процесс:

- загружает акустические веса;
- загружает нужный вокодер;
- выполняет CPU inference;
- отдаёт PCM частями;
- живёт во время серии реплик;
- завершается после TTL;
- при завершении гарантированно возвращает RAM системе.

Такой процессный барьер предпочтительнее надежды на `Dispose`, сборщик мусора и освобождение внутренних аллокаторов Python/PyTorch/ONNX.

## 4. Состояния VoiceHost

```text
Cold
→ EngineReady
→ ModelLoading
→ Ready
→ Speaking
→ IdleWithModel
→ ModelUnloading
→ EngineReady
```

Дополнительные состояния:

- `Cancelled`;
- `Faulted`;
- `ShuttingDown`.

Рекомендуемое поведение:

- VoiceHost запускается вместе с AI_HUB или при первом обращении;
- тяжёлая модель загружается при первой реплике;
- после озвучки остаётся загруженной 30–120 секунд;
- серия близких ответов не вызывает повторную загрузку;
- после TTL worker завершается;
- сохранённый голосовой профиль и конфигурация остаются в лёгком host.

## 5. Стабильный IPC-контракт

Пример команды:

```json
{
  "requestId": "guid",
  "action": "speak",
  "text": "Готово. Результат подготовлен.",
  "voiceProfile": "worker_default",
  "scenarioProfile": "explanatory",
  "style": {
    "pace": 0.96,
    "energy": 0.45,
    "warmth": 0.55,
    "formality": 0.70,
    "pauseStrength": 0.65,
    "emotion": "restrained"
  },
  "streamAudio": true
}
```

Минимальные команды:

- `speak`;
- `stop`;
- `pause`;
- `resume`;
- `unload_model`;
- `health`;
- `list_profiles`;
- `list_components`;
- `get_metrics`;
- `shutdown`.

События:

- `accepted`;
- `model_loading`;
- `model_ready`;
- `audio_chunk`;
- `word_or_segment`;
- `completed`;
- `cancelled`;
- `model_unloaded`;
- `error`.

Основной транспорт на Windows: Named Pipes.
JSON — для команд и метаданных.
PCM — отдельный бинарный pipe либо framed binary messages.
Loopback HTTP допускается только как диагностический режим.

## 6. Собственный Voice Style Profile

Сценарии не должны знать конкретную TTS-модель и писать ей произвольные художественные prompts.

Нужен независимый профиль AI_HUB:

```json
{
  "pace": 0.96,
  "pitch": -0.05,
  "energy": 0.45,
  "warmth": 0.60,
  "formality": 0.70,
  "pauseStrength": 0.65,
  "emotion": "restrained",
  "emphasisMode": "important_terms",
  "delivery": "explanatory"
}
```

Примеры профилей:

- `neutral`;
- `explanatory`;
- `serious`;
- `friendly`;
- `narrative`;
- `alert`;
- `news`;
- `creative`.

Профиль переводится адаптером конкретного backend в:

- параметры акустической модели;
- style embedding;
- speaker embedding;
- SSML или служебные теги;
- настройки постобработки;
- правила пауз и сегментации.

Это позволит менять внутреннюю модель без изменения сценариев.

## 7. Собственная нормализация текста

Этот слой должен принадлежать AI_HUB независимо от выбранной модели.

Задачи:

- удаление непроизносимого Markdown;
- преобразование списков в естественную речь;
- чтение чисел, дат и времени;
- чтение единиц измерения;
- обработка сокращений;
- произношение имён моделей;
- обработка `GGUF`, `Q4_K_M`, `llama.cpp`, `RTX 4090`, `15,4 ГБ`;
- безопасное чтение URL;
- пропуск служебных путей;
- управление ударениями через словарь;
- сегментация длинного ответа;
- различение основного текста, кода, таблиц, источников и предупреждений;
- выбор частей ответа, которые вообще нужно озвучивать.

Принцип:

```text
экранный ответ ≠ текст для TTS
```

Voice Orchestrator должен создавать отдельное речевое представление ответа.

## 8. Кандидаты на компоненты

### 8.1. eSpeak NG — frontend и фонемизация

Роль в будущем стеке:

- text-to-phoneme;
- фонемные коды;
- сведения о pitch и length;
- C API / DLL;
- лёгкий общий компонент.

Официальная документация подтверждает, что eSpeak NG:

- является компактным синтезатором;
- доступен как shared library / DLL;
- преобразует текст в фонемы с информацией о высоте и длительности;
- может быть адаптирован как frontend для другого речевого движка;
- занимает всего несколько мегабайт.

Предлагаемое использование:

```text
AI_HUB TextNormalizer
→ eSpeak NG phoneme frontend
→ собственные словари и исправления
→ нейронная акустическая модель
```

Ограничение: лицензия eSpeak NG — GPL-3.0-or-later. Перед глубокой линковкой с основным приложением требуется повторный лицензионный анализ. Процессная изоляция не отменяет необходимость юридической проверки.

### 8.2. ONNX Runtime CPU — основной inference runtime

Предлагаемая роль:

- CPU inference;
- C#/.NET интеграция;
- кэширование лёгких session-объектов;
- последовательное соединение нескольких моделей;
- переиспользование входных и выходных буферов;
- возможность замены акустической модели без смены VoiceHost.

Официальная документация подтверждает:

- наличие C# API;
- NuGet-пакет `Microsoft.ML.OnnxRuntime`;
- поддержку цепочки `model A output → model B input`;
- возможность переиспользования tensor buffers;
- наличие механизмов настройки производительности, памяти и потоков.

Важное архитектурное решение:

- сам ONNX Runtime может находиться в постоянном VoiceHost;
- тяжёлый `InferenceSession` предпочтительно создавать внутри TtsWorker;
- реальная выгрузка тяжёлых весов обеспечивается завершением TtsWorker.

### 8.3. Piper — референс архитектуры и возможный прототип

Текущий проект Piper развивается в репозитории `OHF-Voice/piper1-gpl`.

Полезные свойства:

- быстрый локальный neural TTS;
- интеграция eSpeak NG;
- C/C++ и Python API;
- локальные модели;
- пригодность для CPU;
- практическое доказательство схемы `eSpeak frontend → компактная модель → waveform`.

Использование в AI_HUB:

- как референс организации runtime;
- как временный прототип;
- как источник опыта по фонемизации и модели;
- не как безусловный фундамент собственного продукта.

Ограничения:

- новый репозиторий имеет GPL-3.0;
- старый `rhasspy/piper` архивирован и указывает на новый проект;
- перед включением кода или моделей требуется отдельный лицензионный аудит;
- центральную архитектуру AI_HUB нельзя жёстко привязывать к текущему состоянию Piper.

### 8.4. HiFi-GAN — первый кандидат на сменный вокодер

Роль:

```text
mel-спектрограмма
→ HiFi-GAN
→ PCM waveform
```

Почему подходит:

- отдельный вокодер;
- известная архитектура;
- высокое качество;
- эффективная генерация;
- открытый официальный репозиторий;
- MIT-лицензия кода официального репозитория;
- может быть отделён от акустической модели.

Риски:

- официальный код ориентирован на Python/PyTorch;
- экспорт конкретной конфигурации в ONNX нужно проверять прототипом;
- лицензии конкретных pretrained weights требуется проверять отдельно;
- нельзя считать CPU-производительность достаточной без замеров на целевом среднем ПК.

### 8.5. OpenVoice V1/V2 — экспериментальный слой тембра и стиля

Полезные заявленные возможности:

- клонирование tone color;
- управление эмоцией;
- управление акцентом;
- управление ритмом;
- управление паузами;
- управление интонацией;
- zero-shot cross-lingual voice cloning;
- MIT-лицензия V1 и V2.

Предполагаемая роль:

```text
базовый русский TTS
→ OpenVoice-подобный tone color converter
→ постоянный голос AI_HUB
```

Ограничение:

официально для OpenVoice V2 нативно перечислены:

- английский;
- испанский;
- французский;
- китайский;
- японский;
- корейский.

Русского в официальном нативном списке нет. Поэтому OpenVoice нельзя заранее считать базовым русским TTS. Он остаётся экспериментальным постпроцессором, который нужно проверять живым сравнением:

- сохраняется ли разборчивость русского;
- не разрушаются ли ударения;
- сколько RAM и CPU он требует;
- можно ли применять его потоково;
- оправдывает ли качество второй проход обработки.

### 8.6. RHVoice — источник сравнительного baseline

RHVoice уже используется в AI_HUB как альтернативный голос ядра.

Официально подтверждено:

- русский является исходным поддерживаемым языком;
- используется statistical parametric synthesis;
- голоса компактны;
- Windows и SAPI5 поддерживаются;
- речь разборчива, хотя менее естественна, чем современные нейронные TTS.

Роль в будущей работе:

- baseline разборчивости;
- baseline холодного запуска;
- сравнение CPU/RAM;
- возможный источник идей по русскому frontend и словарям;
- не основной нейронный голос исполнителя.

Лицензия RHVoice — GPL-2.0. Повторное использование внутренних частей требует отдельной проверки.

## 9. Русская акустическая модель — главный неизвестный компонент

После анализа документации стало ясно, что слабое место не VoiceHost, не IPC и не вокодер.

Главный незакрытый выбор:

```text
русские фонемы
+ speaker embedding
+ style parameters
→ mel или waveform
```

Кандидат должен удовлетворять условиям:

- качественный русский;
- CPU inference;
- небольшой размер;
- разумный cold start;
- работа на среднем игровом ПК;
- отсутствие обязательной CUDA;
- управление темпом, энергией, паузами и хотя бы ограниченным стилем;
- отделение тембра от манеры либо поддержка небольших speaker/style embeddings;
- возможность экспорта или уже готовый ONNX;
- лицензия, совместимая с распространением AI_HUB;
- возможность выгрузки через завершение worker;
- потоковая или сегментная генерация.

До прототипа нельзя фиксировать конкретную модель как окончательную.

## 11. DSP без нейросети

Собственный лёгкий слой:

- нормализация громкости;
- limiter;
- мягкий compressor;
- эквалайзер;
- изменение темпа без изменения pitch;
- fade-in / fade-out;
- удаление чрезмерных пауз;
- кроссфейд между сегментами;
- подавление щелчков на границах;
- выравнивание громкости между сценарными профилями.

DSP не должен маскировать дефекты плохой модели, но может стабилизировать итоговый характер голоса.

## 12. Управление ресурсами

Основные правила:

1. TTS работает на CPU.
2. Базовая архитектура не рассчитывает на свободную VRAM.
3. VoiceHost остаётся лёгким.
4. Тяжёлые веса находятся только в TtsWorker.
5. Worker выгружается по TTL.
6. При нехватке памяти озвучка может быть отключена без остановки основной задачи.
7. Текстовый исполнитель всегда приоритетнее голоса.
8. Нельзя выгружать модель-исполнитель только ради озвучки без явной продуктовой причины.
9. На слабом ПК допускается fallback на RHVoice.
10. Размер и RAM оцениваются по реальному пику, а не только по размеру файла модели.

Метрики обязательного будущего теста:

- размер runtime;
- размер весов;
- cold start;
- warm start;
- RAM до загрузки;
- RAM после загрузки;
- RAM после выгрузки;
- real-time factor;
- загрузка CPU;
- время до первого аудиофрагмента;
- качество русского;
- устойчивость после 50–100 циклов load/unload;
- отсутствие накопительной утечки памяти.

## 13. Установщик и доставка

Основной установщик AI_HUB не должен содержать тяжёлую голосовую модель.

В установщик допустимо включить:

- VoiceHost;
- IPC-контракт;
- лёгкий supervisor;
- конфигурацию;
- базовые профили;
- минимальный runtime, если его лицензия и размер приемлемы.

После подтверждения пользователя отдельно скачиваются:

- выбранная акустическая модель;
- вокодер;
- дополнительные словари;
- optional tone converter;
- voice embeddings.

Каждый компонент должен иметь manifest:

```json
{
  "componentId": "tts-acoustic-ru-default",
  "version": "x.y.z",
  "source": "...",
  "license": "...",
  "sha256": "...",
  "sizeBytes": 0,
  "runtime": "onnx-cpu",
  "languages": ["ru", "en"],
  "status": "installed",
  "lastHealthCheck": "..."
}
```

Установка должна поддерживать:

- подтверждение;
- `.part`;
- resume;
- SHA-256;
- проверку формата;
- health-check;
- статус `runtime_incompatible`;
- удаление;
- обновление;
- rollback.

## 14. Безопасность и приватность

- весь синтез локальный;
- VoiceHost слушает только локальный IPC;
- удалённый сетевой API не открывается;
- текст не отправляется наружу;
- служебные prompts и скрытый контекст не озвучиваются;
- пути к файлам и секреты не попадают в речевой результат;
- TtsWorker запускается с минимальными правами;
- входные команды имеют лимит размера;
- PCM и временные файлы удаляются по политике;
- история озвучки не сохраняется без отдельной причины;
- логируются технические события, но не обязательно полный пользовательский текст.

---

## 15. Что нельзя делать при будущей реализации

- не начинать с обучения модели с нуля;
- не встраивать Python runtime прямо в WPF-процесс;
- не рассчитывать на RTX 4090;
- не держать тяжёлую TTS-модель постоянно в RAM;
- не использовать GPU как обязательное условие;
- не создавать отдельную TTS-модель на каждый сценарий;
- не связывать сценарии с API конкретной модели;
- не считать русский поддержанным только по многоязычному маркетинговому описанию;
- не включать веса в установщик без необходимости;
- не копировать GPL-компоненты в основной процесс без лицензионного анализа;
- не фиксировать OpenVoice как русский baseline без живого теста;
- не считать ONNX-экспорт гарантированным без проверки конкретной модели.

## 17. Критерий успешности идеи

Концепция оправдана, если один голосовой backend:

- работает локально на среднем игровом ПК;
- не использует VRAM как обязательный ресурс;
- сохраняет один узнаваемый тембр;
- меняет манеру речи небольшими профилями;
- обслуживает разные сценарии;
- освобождает тяжёлую память после TTL;
- не заставляет AI_HUB содержать парк отдельных TTS;
- допускает замену внутренних моделей без переделки сценариев;
- звучит заметно естественнее RHVoice;
- остаётся разборчивым на русском;
- не мешает работе текстового исполнителя.

## 18. Предварительный итог

Зафиксированный технический курс:

```text
собственный headless VoiceHost
+ отдельный временный TtsWorker
+ собственная нормализация AI_HUB
+ eSpeak NG как фонемный frontend
+ ONNX Runtime CPU
+ сменная компактная русская акустическая модель
+ HiFi-GAN при необходимости
+ собственные Voice Style Profiles
+ OpenVoice только как поздний экспериментальный слой тембра
```

Это не активное ТЗ. Реализация преждевременна до стабилизации основного сценарного и исполнительного контура AI_HUB.

# Источники, изученные 2026-07-12

Все ссылки следует проверить заново перед началом работ.

1. **eSpeak NG — официальный репозиторий**
   https://github.com/espeak-ng/espeak-ng
   Проверено: компактность, DLL/shared library, phoneme output, pitch/length data, использование как frontend, лицензия GPL-3.0-or-later.

2. **ONNX Runtime — официальная документация C#**
   https://onnxruntime.ai/docs/get-started/with-csharp.html
   Проверено: C# binding, NuGet, inference, chaining моделей, переиспользование tensor buffers, CPU runtime.

3. **ONNX Runtime — официальный индекс документации**
   https://onnxruntime.ai/docs/
   Проверить повторно перед реализацией: управление памятью, threading, profiling, quantization, ORT model format.

4. **Piper — текущий официальный репозиторий**
   https://github.com/OHF-Voice/piper1-gpl
   Проверено: локальный neural TTS, текущая точка развития, GPL-3.0, архитектурная пригодность как референс.

5. **Piper — старый архивированный репозиторий**
   https://github.com/rhasspy/piper
   Проверено: проект архивирован и перенесён в новый репозиторий.

6. **HiFi-GAN — официальный репозиторий авторов**
   https://github.com/jik876/hifi-gan
   Проверено: отдельный neural vocoder, официальный код, MIT-лицензия репозитория. Производительность конкретной CPU/ONNX-сборки требует отдельного теста.

7. **OpenVoice — официальный репозиторий**
   https://github.com/myshell-ai/OpenVoice
   Проверено: tone color cloning, style control, rhythm, pauses, intonation, MIT-лицензия, нативные языки V2. Русский не указан среди нативно поддерживаемых языков V2.

8. **RHVoice — официальный репозиторий**
   https://github.com/RHVoice/RHVoice
   Проверено: statistical parametric synthesis, компактные голоса, русский, Windows/SAPI5, GPL-2.0, baseline для сравнения.

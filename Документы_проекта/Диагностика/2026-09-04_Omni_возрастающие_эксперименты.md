# Omni: возрастающие эксперименты и решение на стенде

Дата: 2026-09-04. Продукт: **0.1.25-dev, не изменён**.
Исследование выполнено по прямому поручению пользователя в режиме «Цель».
В ходе работы пользователь увеличил предельное ожидание этапа с 120 до
**300 секунд**. Это ограничение стенда, не новый лимит приложения.

## Краткий результат

Выделены три разных причины внешнего симптома «нет результата»:

1. **До первого текста:** неэкономичный SDPA/GQA-путь и выход за физическую
   видеопамять. Воспроизведён точно на втором запросе большой картинки:
   анализ завершён, compose за 300 с не дал ни одного текстового фрагмента.
2. **После первого текста:** модель продолжает повторяющийся или выдуманный
   список. На стенде это отдельно обнаружено на карте и зодиакальной картинке.
3. **После конца генерации:** готовый ответ содержит синтаксически неверный
   JSON. Такой случай обнаружен один среди 14 завершённых compose-ответов.

Для первых двух механизмов найдены проверенные на стенде способы улучшения:
экономичный attention и простой первый промпт. Отдельно проверена очистка
неиспользуемого CUDA-кэша между запросами, без выгрузки весов.
**Это не внедрённый патч и не универсальная приёмка качества модели.**

## Условия и методика

- RTX 4090, Qwen2.5-Omni-3B BF16, Thinker-only, весь checkpoint Thinker на CUDA.
- PyTorch 2.11.0+cu130, Transformers 5.16.1, `attention=sdpa`.
- Тот же production worker через stdin/stdout JSONL, без WPF, C#-приёмки
  JSON, Kokoro, загрузки новых моделей или изменения site-packages.
- Перед каждым независимым случаем — новый worker; внутри пары запросов
  модель сохраняется. Последний случай повторён дважды в одном worker.
- Перед прогревами обычно свободно около 22,4–22,7 GiB VRAM. Нагрузка
  фоновой игры отдельно не воспроизводилась; это не обещание тех же цифр
  при занятой видеопамяти.
- Начальная серия: настоящий полный наблюдательный промпт из сохранённой
  сессии `7a238d230b144bb0ab506023b04412db`, текущий ComposeRussian и
  strict/atmospheric/brief/with_title, русский язык, пустые пожелания.
- На втором проходе изображение **по-прежнему присутствует в истории**.
  Отказ от виртуального чата или повторной картинки здесь не внедрялся.
- Затем изменялся только способ подачи grouped key/value в SDPA.
- На двух зациклившихся изображениях отдельно изменён только первый промпт:
  `Опиши, что видишь на изображении.` Второй промпт остался прежним.
- В последнем сравнении добавлено только освобождение unused CUDA cache
  (`gc.collect`, `torch.cuda.empty_cache`) перед запросом.
- Изображения вручную не уменьшались. Штатная предобработка осталась прежней:
  например, исходные 17,3 Мп дают 65048 visual patches, около 16262 image
  tokens. Это не утверждение, что модель обработала каждый исходный пиксель
  5632×3072 без штатного масштабирования.

Стенд фиксировал формы входов, фактический выбор SDPA-диспетчера на этих
формах, CUDA allocated/reserved/peak, nvidia-smi, полный обмен, stream и
снимки стеков через каждые 90 секунд незавершённого запроса.

## 1. Где проходит граница проблем с памятью

Время ниже — **анализ / compose**, без холодного прогрева (~7,1–7,5 с).
«С тем же промптом» означает неизменные инструкции, но не одинаковое число
выходных токенов: разные kernels могут численно менять последующую генерацию.

| Исходное изображение | Размер | Исходный SDPA/GQA | Эксперимент repeat-KV, те же промпты |
|---|---:|---:|---:|
| Маленькое лицо | 251×201; 0,05 Мп | 4,52 / 7,94 с | 4,01 / 5,24 с |
| PNG `416f054e…` | 1254×1254; 1,57 Мп | 17,22 / 25,86 с | 12,90 / 18,52 с |
| Карта `Desktop_260728_0501` | 2937×1296; 3,81 Мп | 9,89 / 11,66 с | 7,53 / 7,87 с |
| Карта `Desktop_260728_0454` | 3175×1672; 5,31 Мп | 12,94 / **84,11 с** | Начал текст за 2,15 с, затем повторял названия; остановлен |
| Девушка | 3072×2048; 6,29 Мп | 18,53 / **нет текста за 300 с** | 13,15 / 15,76 с; JSON со скобочной ошибкой |
| Чёрный кот | 3497×1960; 6,85 Мп | Не запускался повторно в этой серии¹ | **7,61 / 9,71 с** |
| Иллюстрация «Вий» | 3840×2160; 8,29 Мп | Не запускался | **18,85 / 29,57 с** |
| Зодиак | 5632×3072; 17,30 Мп | Не запускался | Первый текст за 5,96 с, затем выдуманный список; остановлен |

¹ Предыдущий прямой прогон кота остановлен после 120 с ещё в первом
prefill. См. `2026-09-04_Omni_прямой_тест_SDPA.md`. В текущей baseline-серии
рост остановлен при первом 300-секундном отказе, не прогонялись заведомо
более тяжёлые baseline-картинки ради повторения того же симптома.

**Перелом в этой серии:** 7810 входных токенов на втором проходе карты
привели к 72,868 с ожидания первого текста; 9204 на втором проходе девушки —
к отсутствию текста за 300 с. При этом первый проход девушки с 8411 токенами
завершился за 18,533 с. Значит, это **не универсальный порог числа пикселей
или токенов**: важны форма входа, состояние allocator после первого прохода
и свободная физическая VRAM.

### Конкретная вычислительная точка

Второй запрос девушки успел повторно пройти визуальную часть и дошёл до
текстового attention: query `[1,16,9204,128]`, key/value `[1,2,9204,128]`,
BF16, causal, без маски, `enable_gqa=True`. Выбран backend **0 / MATH**.
На снимках стека поток генерации находится в SDPA внутри `_prefill`, а
поток протокола ожидает streamer. Ни готового JSON, ни первого текста нет.

Причинная цепочка, поддержанная измерениями:

`длинный вход + GQA → MATH → большие временные тензоры и резерв allocator
→ выход за физическую VRAM → очень долгий prefill`.

## 2. Измерения памяти

| Случай / этап | Зафиксированный пик allocated | Максимум reserved в отметках |
|---|---:|---:|
| Baseline 3,81 Мп, compose | 14,03 GiB | 17,70 GiB |
| Baseline 5,31 Мп, compose | 17,92 GiB | **24,78 GiB** |
| Baseline 6,29 Мп, compose, незавершённый | ≥20,98 GiB | ≥30,65 GiB |
| Repeat-KV 6,29 Мп, compose | **11,86 GiB** | 15,77 GiB |
| Repeat-KV 6,85 Мп, compose | 12,04 GiB | 16,30 GiB |
| Repeat-KV 8,29 Мп, compose | 12,73 GiB | 17,82 GiB |
| Repeat-KV + простой промпт, 17,30 Мп, compose | 14,52 GiB | 22,21 GiB |
| То же + очистка unused cache, 17,30 Мп, compose | **14,52 GiB** | **17,68 GiB** |

Знак ≥ у оборванного случая означает: последняя отметка не гарантирует
окончательный пик всего незавершённого запроса.

Для зависшего baseline worker PID 36428 отдельный Windows GPU-счётчик дал:

- DedicatedUsage: 23 848 824 832 байт ≈ 22,21 GiB;
- SharedUsage: 9 539 944 448 байт ≈ 8,89 GiB;
- TotalCommitted: 33 455 878 144 байт;
- процесс WorkingSet: 11 645 792 256 байт; PrivateMemorySize: 37 530 112 000 байт.

Это подтверждает использование shared GPU memory, а не только показание
«GPU 100%». Allocated, reserved, dedicated/shared и working set — разные
метрики, их нельзя суммировать как независимые расходы. Большой reserved
не означает, что сами веса модели выросли или что все байты заняты живыми
тензорами. После завершённых запросов allocated возвращается примерно к
9 424 200 192 байт (8,78 GiB), то есть основная масса — освобождённый резерв,
а не подтверждённая утечка живых данных между запросами.

## 3. Проверенное изменение attention

В установленном torch `flash_sdp_enabled=True`, но
`is_flash_attention_available=False`: Flash kernel не скомпилирован.
Transformers разрешает GQA для CUDA без маски и передаёт 16 query-heads / 2
KV-heads. В этом окружении такой вызов выбирает MATH, а не быстрый kernel.

**Стендовый вариант:** повторить каждую KV-head для соответствующей группы
query-heads и вызвать тот же SDPA без `enable_gqa`. Для этих входов выбирается
**2 / EFFICIENT_ATTENTION**. Число весов, размер картинки, EOS, модель,
язык и инструкции от этого не меняются. Это не «удаление экспертов» и не
перенос расчётов на CPU.

Дополнительный CPU-event profiler на небольших CUDA BF16 тензорах подтвердил
не только значение селектора, но и вызываемые операции:

```text
original: aten::_scaled_dot_product_attention_math
expanded: aten::_scaled_dot_product_efficient_attention
          aten::_efficient_attention_forward
```

Проверка математического соответствия:

- 6 CPU-пар: FP32/BF16, prefill и одиночный decode, causal/non-causal;
  разность нулевая;
- 6 CUDA-пар: максимальная абсолютная разность FP32 ≤1,91e-6,
  BF16 ≤0,0078125; проверки допустимой численной погрешности пройдены;
- это **не гарантия побитового совпадения ответов**: небольшие различия
  вычислений могут менять выбранный следующий токен и дальнейший текст.

Рекомендация для будущего внедрения: ограничить адаптацию Heavy и проверять
реальную доступность kernels. Не переносить глобальный monkeypatch стенда
в приложение, не редактировать установленные site-packages, не навязывать
этот путь окружениям с нормально работающим Flash. Другие модели и платформы
в этой серии не тестировались.

## 4. Вторая причина: бесконечное расширение ответа

После экономичного attention две картинки больше не зависали в prefill,
но полный промпт «исследуй максимально всё» приводил к повторяющемуся выводу:

- карта 5,31 Мп: более 10000 символов, многократный повтор одних названий;
- зодиак 17,30 Мп: более 5200 символов, сотни выдуманных лет/строк «Пчела»
  при 12 животных на изображении.

Оба потока остановлены вручную до 300-секундного максимума после фиксации
повторений. EOS в worker передаётся; факт повторения не объясняется старым
дефектом отсутствующего EOS. Модель просто ещё не сгенерировала конец ответа.
Это отличающийся от заполнения памяти механизм. Нельзя утверждать, что
одна фраза промпта — единственная универсальная причина всех подобных петель.

Контрольный первый промпт: **«Опиши, что видишь на изображении.»**
Второй промпт, картинка и repeat-KV оставлены прежними.

| Случай | Анализ | Compose | Результат |
|---|---:|---:|---|
| Карта 5,31 Мп, простой первый промпт | 6,047 с | 7,331 с | EOS, JSON извлекается |
| Зодиак 17,30 Мп, простой первый промпт | 19,859 с | 14,262 с | EOS, JSON извлекается |
| Зодиак + очистка unused cache, повтор 1 | 20,009 с | 14,410 с | EOS, JSON извлекается |
| Тот же загруженный worker, повтор 2 | 19,437 с | 13,789 с | EOS, JSON извлекается |

В последнем сравнении анализ и compose **посимвольно совпали** во всех трёх
успешных проходах зодиака (до очистки и дважды с очисткой).
Очистка снижает резерв примерно на 4,53 GiB; холодный прогрев повторно не
выполнялся. Замеры окончания без очистки: свободно 292 MiB VRAM; с очисткой
на окончаниях/между повторными запросами — примерно 4–5 GiB.
Времена worker не включают ~0,1 с диагностической очистки; полные wall-time
доступны в выводах стенда. Уменьшение промпта — изменение задания модели,
а не доказательство сохранения прежней полноты наблюдательного отчёта.

## 5. Качество и JSON: что не вылечено

Из 14 завершённых compose 13 содержат извлекаемый JSON. Markdown-ограждения
не считались ошибкой: приложение умеет извлекать объект из них.
Это синтаксическая проверка, не запуск всей C#-валидации и не приёмка UX.

У девушки в repeat-KV-ветке после строки paragraphs закрывающая `]`
присутствует дважды. Ответ завершён по EOS, но JSON действительно неверен.
Его отклонение приложением было бы **другим случаем**, не 300-секундным
ожиданием worker. Стенд ответ не исправлял и не подменял.

При осмотре зодиака подтверждены содержательные ошибки: модель называет
2028 год овцой вместо изображённой обезьяны, а всю картинку — календарём
на 2036 год, хотя там диапазон 2026–2037. Заголовки при with_title также
часто остаются null. Качество OCR, следование настройкам и формат ответа
остаются отдельными задачами. Kokoro не тестировалась и не менялась.

## Предлагаемое следующее решение

На стенде рациональна комбинация:

1. Экономичный attention для текущего проблемного GQA-пути.
2. Освобождение ненужного CUDA allocator cache между самостоятельными
   запросами, с сохранением загруженных весов.
3. Более конкретный наблюдательный запрос вместо требования бесконечно
   расширять исследование; окончательную формулировку ещё согласовать по ТЗ.

Повторная картинка сама по себе не делает сценарий неработоспособным:
с ней получены оба завершённых этапа даже для крупнейшего исходника серии.
Это не отменяет потенциальную пользу текстового второго прохода, но теперь
отказ от картинки не выглядит обязательным обходом неизвестного зависания.

**В AI HUB ничего из этого не внедрено.** Все инструменты и варианты
изолированы в `Инструменты/tests`. Системные настройки, модель, её файлы,
библиотеки, Medium, Kokoro, VERSION и installer не менялись.

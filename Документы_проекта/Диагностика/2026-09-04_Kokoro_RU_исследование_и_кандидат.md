# Kokoro RU: локализация аварии и проверенный кандидат обхода

Обновление статуса: выводы согласованы, обход внедрён в 0.1.27-dev и принят
пользователем после одного теста без ошибок. См.
[закрытое ТЗ лечения](../../ТЗ/Архив/2026-09-04_лечение_загрузки_Kokoro_RU.md).
Ниже сохранён исторический отчёт до внедрения. Его команды контроля относятся
к прежнему исходнику worker: текущие baseline/decoder-control уже включают
production helper и не являются исходным вариантом без исправления.

Дата: 2026-09-04. Продуктовый baseline: **0.1.26-dev**, HEAD `52413b9`.
Исследование начато в 22:57 UTC+07 по поручению пользователя с пределом
около 30 минут. Приложение, Omni и игра не запускались. Код продукта,
установленные пакеты и файлы моделей не менялись.

## Результат

Поймана нативная авария `0xc0000005` при загрузке быстрого токенизатора
модели омографов RUAccent. Она возникает **до обработки пользовательского
текста, синтеза WAV и воспроизведения**. Получен стек Python, подтверждённый
новым событием Windows. Само имя tokenizers больше не является единственным
свидетельством.

Проверен узкий стендовый обход повторного построения таблицы добавленных
токенов. Он сохраняет весь сериализованный токенизатор и контрольные
результаты, сокращает холодный RU-старт с 25,7–26,4 до 10,2 с и прошёл
3 холодных RU-запуска / 12 синтезов плюс 3 EN-запуска / 6 синтезов.

**Это кандидат обхода и подтверждённое ускорение, а не доказательство
устранения всех нативных аварий.** В согласованном контрольном проходе
исходный вариант тоже прошёл три запуска. Причина повреждения памяти
внутри native-кода пока не установлена. В приложение обход не перенесён:
по активному ТЗ сначала согласуется результат исследования.

## Зафиксированная авария

Запуск: `trace_sessions/trace_ru_1`, запрос `load`, без текста.
Worker launcher PID 760; Windows сообщает фактический Python PID `0x1690`
(5776). В Windows venv python.exe запускает дочерний базовый Python, поэтому
путь AppPath к общему Python312 ожидаем и не означает другое окружение.

- В 23:05:27, примерно на 5,4 с процесса: вход в RobertaTokenizerFast.
- Стек: `RUAccent.load` → `OmographModel.load` →
  `AutoTokenizer.from_pretrained` → `PreTrainedTokenizerFast.__init__`
  (строка 172) → `added_tokens_decoder` (строка 243) →
  native `get_added_tokens_decoder()`.
- Windows Event 1000: `2026-09-04T16:05:35.1604490Z`, RecordId **132832**,
  `tokenizers.cp312-win_amd64.pyd`, offset `0x17b80d`,
  exception `c0000005`, report `d621e4cc-c378-49a8-84de-0137a7ec7673`.
- Родитель получил EOF через 18,641 с; код **3221225477 / 0xc0000005**.
  Разница со временем последнего Python-события включает оформление аварии
  Windows и завершение процесса; её нельзя считать временем полезной работы.

Ранее исправленный `_CompatibleTokenTypeIdsShim` сохранён. Новый стек
относится к загрузке, а известное исключение о недостающем token_type_ids —
к инференсу ударений. Эти дефекты не объединяются.

## Кандидат и его границы

В checkpoint есть 10002 записи старого added_tokens.json и 10007 записей
в tokenizer.json. Вторая таблица уже содержит все необходимые токены.
Transformers 4.41.2 при согласовании старого формата многократно обращается
к added_tokens_decoder внутри цикла. Tokenizers 0.19.1 каждый раз создаёт
новую таблицу обёрток. Для этого файла получается порядка 100 миллионов
создаваемых записей за загрузку — вывод из кода и размеров таблиц.

Стендовый вариант передаёт `added_tokens_decoder={}` только при загрузке
локального `nn_omograph/turbo3.1`, предварительно проверяя, что все старые
токены имеют те же ID в tokenizer.json. Токены не удаляются: полная таблица
продолжает читаться из tokenizer.json. Остальные токенизаторы не меняются.
Обёртка действует только внутри диагностического дочернего процесса.

Проверки эквивалентности:

- совпали количество токенов, added tokens и вся сериализация backend;
  общий SHA-256 `00911401812289c0ab07df113db2c04a1c60ad9d475215cc275f28e8b5d5b99a`;
- совпали input IDs, attention mask и offsets для шести фраз, включая
  омографы, маркеры `<w>`, ё, ударение и редкие имена;
- совпали хеши фонем двух пользовательских сводок между контролем и
  кандидатом, включая все тёплые повторы;
- все **57 WAV** всего исследования: 24 kHz, mono, ненулевой конечный
  сигнал. Слуховая оценка качества и UI-воспроизведение не выполнялись.
  Побайтовая идентичность WAV не требовалась.

| Сопоставимый замер | Без обхода | С обходом |
|---|---:|---:|
| Холодный RU-старт, родительский секундомер | 25,656–26,375 с | 10,156–10,266 с |
| Холодный EN-старт, тот же стенд | 6,641–6,765 с | 6,703–6,843 с |
| Пик RAM полного RU-процесса | 3,232–3,247 GiB | 3,234–3,248 GiB |

Заметного снижения постоянной памяти нет. В RU-процессе наблюдалось до
178 потоков, но причинная связь числа потоков с crash не доказана.
Первые серии измеряли память venv-launcher, а не дочернего Python: их поля
memory не используются для выводов о RAM. Последующие processSamples
содержат оба PID; таблица выше использует фактический Python-процесс.

## Повторная подготовка Heavy: отдельный результат

Соседний дефект **сохранился** в актуальном коде:

1. `MainWindow.ImageAnalysisLiterary.cs:826` ждёт Kokoro перед фоновой
   подготовкой, но ручной анализ имеет свой EnsureWorkerReadyAsync.
2. `OmniHeavySingleImageLiteraryPipeline.cs:31` без проверки готовности
   вызывает PrepareAsync и перезаписывает _warmup.
3. `Qwen25OmniRuntimeService.cs:72` пересчитывает план и назначает CurrentPlan
   **до** semaphore на строке 87. Это допускает замер уже занятой VRAM.
4. `qwen25_omni_worker.py:439` возвращает alreadyLoaded=true и load=0,
   если нужный профиль уже загружен; повторная загрузка весов не требуется.
5. `OmniHeavySingleImageLiteraryPipeline.cs:240` переносит этот ноль в метрики.

Это отличается от исправленных EOS/SDPA/cache. Минимальный будущий патч:
объединить одновременные вызовы подготовки, проверять готовность и считать
план под одной блокировкой, сохранять метрики первой физической загрузки.
В этом исследовании соседний код не исправлялся и Omni не запускалась.

## Следующий шаг и откат

После согласования вывода можно перенести **только** проверенный адаптер
загрузки RU-токенизатора в отдельный helper worker. Ограничить его известной
версией/структурой checkpoint, оставить проверку полноты таблицы, явно
логировать применение. Не обновлять общий reranker и не подменять RU-голос.
Отдельно целесообразно сохранять native exit code/PID и faulthandler при
пользовательском сбое, чтобы проверить оставшуюся неопределённость.

Для утверждения устойчивости нужен последующий пользовательский запуск
через AI HUB. Отсутствие аварий в трёх запусках кандидата не заменяет эту
проверку. Повторные автостарты worker сами по себе лечением не считаются.

Backup до работ: `_backups/20260904_kokoro_30min_research`, включая прежнюю
историю, ТЗ и worker. Стенд не меняет site-packages и модели, поэтому
runtime-откат не нужен. Скрипты находятся в `Инструменты/tests/`:
run_kokoro_crash_probe.py, kokoro_probe_child.py, kokoro_probe_metrics.py,
summarize_kokoro_probe.py. Они запускаются только вручную.

Воспроизведение на этом ПК, с новым именем выходной папки:

```powershell
& 'Runtime/Python/reranker/.venv/Scripts/python.exe' `
  'Инструменты/tests/run_kokoro_crash_probe.py' `
  --output 'Тесты/Kokoro_research_20260904/new_control' `
  --input 'Тесты/Kokoro_research_20260904/session_inputs.json' `
  --variant decoder-control --languages ru --cold-repeats 3 `
  --warm-repeats 2 --timeout 90 --budget-seconds 300
```

Для единственного изменения использовать `--variant decoder-bypass` и
другую новую папку. Вариант `baseline` запускает исходный worker напрямую;
`trace` добавляет только наблюдение этапов. Параллельно серии не запускать.

Первичные протоколы: `Тесты/Kokoro_research_20260904/`, не публиковать целиком.
Там сохранены окружение, команды, PID, запросы/ответы, stderr, WAV,
целостность файлов, события Windows и summary.json. Дампы памяти не снимались.

Проверки стенда: py_compile четырёх скриптов; анализ всех 36 результатов и
57 WAV; сравнение backend/токенизации/фонем; git diff --check и UTF-8.
Сборка приложения и .NET-тесты не повторялись: продуктовый код не менялся.
Установщик не собирался по правилу. Commit/push и архивации ТЗ не было.

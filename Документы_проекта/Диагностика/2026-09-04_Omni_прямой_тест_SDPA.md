# Прямой тест большого изображения: вычисления SDPA

Дата: 2026-09-04. Приложение: 0.1.25-dev, рабочий код не менялся.
Пользователь разрешил прямое воспроизведение и ограничил ожидание зависшего
этапа двумя минутами. Только один прогон модели; Kokoro не запускалась.

## Метод

- Тот же `qwen25_omni_worker.py`, вызываемый напрямую по его штатному
  stdin/stdout JSONL-протоколу, без WPF и C#-валидатора результата.
- Модель Qwen2.5-Omni-3B BF16, Thinker-only, CUDA-only, SDPA.
- Runtime: Python 3.12, torch 2.11.0+cu130, Transformers 5.16.1.
- Большой кот 3497×1960 из сохранённой сессии
  `7a238d230b144bb0ab506023b04412db`. SHA-256:
  `849657eebcee7d2654905fafd60280874a78be061ff6a784dd10d1b4984b0d8c`.
- Настоящий наблюдательный промпт из сессии, без сокращения. Второй запрос
  приготовлен с текущим ComposeRussian и исходными настройками
  strict/atmospheric/brief/with_title, но до него выполнение не дошло.
- Изолированная диагностическая обёртка добавляет отметки начала generate,
  форм тензоров SDPA, показателей CUDA allocator и снимок всех стеков на 90 с.
  Параметры генерации, картинка, EOS, выбор backend не заменялись.
- GPU-бюджет загрузки 20 GiB, CPU 60 GiB; карта размещения целиком cuda:0.
  Это не запуск планировщика ресурсов интерфейса и не точная копия нагрузки
  пользовательского приложения. Перед стартом свободно около 21,95 GiB VRAM.

**Похожая остановка воспроизведена вне интерфейса, но уже на первом
проходе. Точное зависание только второго прохода этим тестом не доказано.**
Протокол передал изображение, обработчик создал `pixel_values [35000,1176]`,
`image_grid_thw [1,3]`, `input_ids [1,9131]`. Модель выполнила визуальные
attention-вызовы и дошла до обработки 9131 входного токена текстовой частью.
Следовательно, в этом прогоне проблема не в недоставленной картинке и не в
отказе C# принять уже готовый JSON. Нет оснований считать отсутствие ответа
долгим самостоятельным «размышлением»: на 90-й секунде шла обработка входа.

## Обнаруженная проблема выбора вычислительного механизма

У зафиксированного текстового attention входы:
`query [1,16,9131,128]`, `key [1,2,9131,128]`, BF16, causal, без маски.
Это grouped-query attention: число query-голов и key/value-голов различается.

Установленный `transformers/integrations/sdpa_attention.py` при этих условиях
передаёт `enable_gqa=True`, не разворачивая key/value заранее.

Отдельная короткая проверка **без модели и без вычисления attention** дала:

```text
flash_sdp_enabled = True
is_flash_attention_available = False
can_use_flash_attention = False
Warning: Torch was not compiled with flash attention.
can_use_efficient_attention = False
Warning: ... require query, key and value to have the same num_heads.
can_use_cudnn_attention = True
cudnn_sdp_enabled = True
_fused_sdp_choice(original GQA shapes) = 0 (MATH)
_fused_sdp_choice(explicitly repeated key/value heads) = 2 (EFFICIENT_ATTENTION)
```

`can_use_cudnn_attention=True` не означает, что этот kernel выбран:
селектор фактически вернул MATH. Аналогично разрешающий флаг Flash не
означает наличие Flash в бинарной сборке PyTorch.

**Подтверждено:** несовпадение флага Flash и реальной доступности; выбор
MATH селектором для синтетических входов с теми же размерами/типом и GQA;
большой временный расход памяти и незавершённый prefill в прямом прогоне.
Точный CUDA-kernel в самом модельном прогоне профилировщиком не записывался.
Совместно это сильная улика в пользу неэкономичного пути SDPA как причины
замедления больших картинок, а не окончательное доказательство всех прошлых
зависаний или проблемы исключительно второго запроса.

## Следующий кандидат — пока не внедрён

Проверить штатно эквивалентное разворачивание key/value-голов перед SDPA
для этого окружения, чтобы не попадать в MATH при GQA. В установленном
Transformers уже есть ветка `repeat_kv` для других условий; кандидат не
требует изменения весов, промптов, числа токенов или разрешения картинки.
Селектор на таких входах выбирает EFFICIENT_ATTENTION, но скорость, качество
и устойчивость модели ещё не проверены. Переключать глобальные настройки,
править site-packages или устанавливать FlashAttention в этом проходе не стали.
Отказ от повторной подачи картинки остаётся отдельным предложением, а не
проверенным данным тестом исправлением.
